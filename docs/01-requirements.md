# 需求说明（题1：素材审核与发布排期 Agent）

## 1. 用户与目标

**用户**：内容团队的运营人员。每天有一批待发布的素材（短视频、图文），需要判断每条能否发、
发在什么时间，并整理成一份可确认的排期。

**当前痛点**：素材的发布时间有硬性要求（配合活动、投放、客户约期），但同一渠道的时段有限。
人工核对容易出现三类问题——把有风险的素材排进去、把硬性时间悄悄改了却没告知、
同一个素材被提交两次生成两条排期记录。

**目标**：给定一批素材与已有的排期表，输出每条素材的审核结论与建议时段，
并在**不获得用户确认的前提下**绝不把改动当作既成事实。

**关键的业务前提**：本系统**只保存草稿，不接真实发布**。
系统里不存在"发布"这个能力，也不存在能把草稿变成已发布的代码路径。

## 2. 输入与材料

| 输入 | 说明 | 文件 |
|---|---|---|
| 素材清单 | 素材 ID、标题、渠道、要求发布时间、硬性标记、元数据、内容特征 | `data/assets.json` |
| 补充材料 | 用于"补查"的额外字段，**不含**某些素材（用于制造补查无果） | `data/asset_extra.json` |
| 审核规则 | R1 四要素齐全、R2 未核实效果数据、R3 连发间隔、R4 发布时段 | `data/rules.json` |
| 已有排期 | 按渠道/日期/时段记录占用情况 | `data/schedule.json` |
| 故障注入 | 指定哪些素材的保存会失败 | `data/failure_config.json` |

素材共 7 条（M01–M07），每条对应一个必须验收场景，映射见 `06-task-plan.md` 第 3 节 T1。

## 3. 可用工具

系统向模型暴露五个工具，全部是本地实现：

| 工具 | 作用 | 典型失败 |
|---|---|---|
| `list_pending_assets` | 取本批待处理素材 | — |
| `get_asset_detail` | 读元数据并合并补充材料，返回缺失字段 | 素材不存在 |
| `check_rules` | 返回**全部**命中规则及等级 | 素材不存在 |
| `query_slots` | 返回某渠道某日的占用与可用时段 | 渠道/日期不存在 |
| `save_draft` | 保存草稿（幂等） | 规则阻断、写盘失败、锁冲突 |

工具不提供、也不接受任何"发布"参数。

## 4. 交付结果

每条素材输出五项，字段与 `docs/02-solution.md` §4.10 一致：

1. **审核状态**（`passed` / `blocked` / `needs_info`）
2. **风险原因**（含规则编号，如 `R2: 命中未核实内容特征`）
3. **建议时段**（与用户原始要求分开存放，永不合并）
4. **待确认项**（改期必须在此列出原因）
5. **草稿保存状态**（`draft_saved` / `failed` / `blocked` / `not_attempted`）与 `draft_id`

另有一条恒定字段 `able_to_publish`，值恒为 `false`。

## 5. 范围

**做**：素材读取、规则检查、时段冲突识别与替代时段建议、草稿保存与幂等、
逐素材状态上报、执行预算与超限收口、决策轨迹与审计记录。

**不做**（明确排除）：

- 真实发布接口——题目要求仅保存草稿，实现发布会自己制造越权风险；
- Web 界面与线上部署——题目明示非必需；
- 多 Agent 编排——单 Agent 已覆盖全部验收点，多 Agent 会稀释轨迹可读性；
- 跨素材的时段唯一性——属于调度层的排他判断，草稿层只保证"一素材一草稿"。

## 6. 成功标准

以下每条都能用仓库内的命令复核，不需要口头说明。

| 编号 | 成功标准 | 复核方式 |
|---|---|---|
| S1 | 无风险的素材按时段可用性得到排期或改期建议 | `examples/run_normal.txt`、`run_conflict.txt` |
| S2 | 信息缺失的素材被阻断，且补查无果时不留草稿 | `examples/run_missing_info.txt` |
| S3 | 补查有来源的素材能补齐并正常排期 | `examples/run_missing_info_resolved.txt` |
| S4 | 命中阻断规则的素材不得排期 | `examples/run_rule_risk.txt` + `audit.jsonl` |
| S5 | 时段被占用时改期，且必须标记待确认 | `examples/run_conflict.txt` |
| S6 | 重复提交同一请求只产生一份草稿 | `run_conflict.txt` 的「重复提交校验」 |
| S7 | 保存失败明确返回失败，不产生草稿、不虚报成功 | `examples/run_save_failure.txt` + `audit.jsonl` |
| S8 | 任何输出都不出现"已发布/发布成功"等语义 | `examples/unittest_output.txt` 中的 `test_no_publish_word` |
| S9 | 执行有上限，触达后返回结构化未完成 | `tests/test_runtime.py` |
| S10 | 至少两条路径体现"因工具结果调整动作" | `tests/test_examples_evidence.py` 的两条断言 |

## 7. 非功能要求

- **诚实优先**：输出由结构化结果渲染，不采信模型的自然语言；命中禁词即拒绝输出（退出码 2）。
- **可离线**：不配置任何环境变量即可运行全部用例与测试（`--offline`）。
- **零第三方依赖**：测试用标准库 `unittest`，评审 clone 后无需 `pip install`。
- **有界执行**：全局 80 步、单素材 8 步、60 次工具调用、120 秒墙钟，任一触达即收口。
- **可审计**：每次工具调用落 `examples/audit.jsonl`，保存失败也留痕。

## 8. 已知边界

本仓库的 `examples/` 全部来自离线 Mock 规划器。它证明流程、护栏、幂等与失败上报，
**不证明真实模型的决策质量**。真实模型轨迹需配置 `OPENAI_API_KEY` 后自行生成，
详见 `03-evaluation.md` 第 5 节。
