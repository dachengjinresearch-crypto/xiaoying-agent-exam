# 回顾（最难的问题、学习收获、下一步）

## 1. 最难的问题

### 1.1 幂等的最难之处不在"重复"，在"并发"

最初以为幂等就是"查一下有没有，有就返回旧的"。写完第一版测试全绿，
直到专门造了一个场景：两个 `DraftService` 实例共享同一份草稿文件。

结果是 96 次并发写只剩 12 份草稿，更糟的是 `draft_id` 被**重用**——
两个素材指向同一个编号。这不是"少了几条数据"，而是数据完整性问题。

分两层修复：

- 写入前比对文件 `(mtime_ns, size)` 签名，变了就重读，挡住"先后覆盖"；
- 再用 `O_CREAT|O_EXCL` 锁文件把读-改-写包成临界区，挡住"同时覆盖"。

签名这一层单独是不够的——真并发探针显示它挡不住同时写，这说明**"看起来正确"和"并发下正确"是两件事**。

### 1.2 失败路径比成功路径更容易说谎

锁文件一开始放在数据目录里。在受限挂载点上，删除被拒绝（`EPERM`），
而删除写在 `finally` 里，于是**清理动作失败把一次已经成功的写入报成了失败**。

更隐蔽的是第二个问题：代码只把 `E_STORAGE_WRITE` 记成 `failed`，
锁冲突返回的 `E_STORAGE_LOCK` 既不标成功也不标失败，最终 UI 上显示"未处理"。
素材被静默吃掉了。

这两处的共同点：**错误处理本身制造了新的错误信息**。
最后定的规则是——清理尽力而为，绝不影响业务结论；任何保存失败都必须留下 `failed` 痕迹。

### 1.3 预算差点让功能"看起来没做完"

架构里写的是 `MAX_STEPS = 12`，看起来很合理。实测全量跑一遍是 33 步。
按 12 步，运行会在第 3 个素材处截断，返回 `incomplete`，后四个场景根本不会被验证。

改成双层：全局 80 步防死循环，单素材 8 步防额度被单个素材吃光。
这提醒我：**上限不该拍脑袋定，要先量一条完整链路的成本**。

## 2. 关键取舍复盘

**护栏放代码还是放提示词。** 提示词里写"不许越权"很省事，但那只是请求模型自律。
最终把允许动作做成一张矩阵，`BLOCKED` 状态的集合里没有 `save_draft`——
越权在结构上就不可能发生。提示词只负责减少无效尝试，不承担安全责任。

**改期要不要自动标记待确认。** 让系统自动补 `pending_confirmation` 更"省事"，
但那样模型的行为看起来像"我直接改了时间"，评审会认为是擅自改期。
最终选择拒绝，让模型自己修正参数——这条路径反而成了 ReAct 的证据。

**Mock 能不能算决策证据。** 不能。它内部是规则分支，只能证明流程通、护栏拦得住。
所以在文档里反复标注"不构成真实模型决策效果的证明"。
如果强行包装，省下的解释成本远小于被识破的代价。

## 3. 学习收获

1. **"不虚报"要落到代码结构上，而不是靠自觉。**
   草稿对象有 `able_to_publish` 常量字段、工具签名里没有发布参数、
   输出层拒绝禁词——三处都是结构性的，不依赖任何一次正确的判断。

2. **验证要能证伪。**
   只跑正向用例说明不了检查器在工作。给禁词扫描器故意塞一句"已发布"，
   确认它会报错；确认只污染说明行时不会误报。这一步比多写十个用例更有信息量。

3. **边界要写进测试，而不是写在注释里。**
   草稿层不校验跨素材时段唯一性，这是有意的。把它写成一条测试并注明理由，
   比在注释里叹一句"这里没做"要可靠得多。

4. **文档和代码会漂移，测试不会。**
   任务文档里原本写的测试文件名（`test_save_failure.py` 等）与实际文件对不上，
   是回看时才发现的。最终以实际文件为准更新了文档。
