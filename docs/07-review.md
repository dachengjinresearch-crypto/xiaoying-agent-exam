# 设计复查记录（v0.1 → v0.2）

> 本文件记录架构与任务拆分完成后的**一轮对照题意的独立复查**，包括发现的问题、处理方式与验证方法。
> 复查对象：`02-solution.md`、`06-task-plan.md`
> 判据：笔试题原文"1项目题 · 100分 素材审核与发布排期 Agent"一节，以及考核总则中的 Agent 决策要求。

---

## 1. 复查方法

分三步，避免"自己写自己评"的盲区：

1. **独立视角复查**：把两份文档交给一个不带写作上下文的审查者，只给题目原文作为唯一判据，
   要求按"题意不符 / ReAct 硬要求 / 一票否决风险 / 过度设计 / 遗漏 / 内部矛盾"六类提出问题。
2. **逐条核验**：对每条意见回到原文与文档定位，判断是真实缺陷还是误判，**不盲从**。
3. **修正并留痕**：采纳的改文档，不采纳的写明理由，避免下一轮重复讨论。

## 3. 未采纳的意见与理由

| 意见 | 不采纳理由 |
|---|---|
| "建议补任务覆盖路径穿越、数据外泄、伪造成功" | 不作为独立任务，而是写进 T7/T12 的实现要点与 §7 归口表。理由是这三项实现成本低于 5 分钟，单独立项会稀释任务粒度；但必须有归口，不能只挂设计 |
| "建议把 Validator 的 schema 校验降为 P1" | 不降。Validator 是"模型输出不可信"的唯一结构防线，且实现量小（约 20 行），降级风险高于收益 |
| "建议删除 Metrics" | 采纳，但未单列。原始设计中 Metrics 只是运行结束打印的 dict，不构成独立任务，已在 T13 之外省略 |

## 4. 修正后的验证方式

修正不能只写在文档里，必须有可检查的落点：

| 修正项 | 验证方式 | 通过标准 |
|---|---|---|
| A1 五项交付字段 | 看 `run_normal.txt` 的 OUTPUT 段 | 五项字段逐条出现，且 `requested_publish_at ≠ suggested_slot` |
| A2 `hard_requirement` | T1 验收脚本断言 | M01 该字段为 `true` |
| A3 补查有来源 | 对比 M03 与 M07 输出 | M03 补查后仍缺；M07 补查后补齐 |

| B1 Mock 边界 | 读 README 与 `docs/03-evaluation.md` | 两处均有"离线仅验证流程"表述；真模型 trace 单列 |

| C2 不静默替换 | 构造含禁词的输出 | 抛 `HonestyViolation` 且 audit 有记录，输出未被"改写后照常返回" |

| F1 枚举统一 | `grep -r "needs_manual" src/` | 无匹配 |

## 5. 遗留风险（已知且接受）

1. **P0 仍需约 175 分钟**，缓冲只有 4 分钟。任何一段超时都会挤压后面的验证时间。
   缓解手段是 §5 的裁剪顺序与两条熔断线，而不是继续压缩任务。
2. **真模型轨迹的取得依赖 API 可用性**。若不可用，只能如实标注"ReAct 未实证"。
   这会在评分上直接损失 ReAct 那一项，但比用 Mock 冒充诚实。
3. **离线与在线两条路径的 trace 形态可能不同**（Mock 的 `reason` 措辞更机械）。
   评审若只看到 Mock，可能误判为固定分支。因此 README 必须把边界写在第一屏，而不是藏在 docs 里。
4. **护栏过严**会拒绝一些合法但非常规动作，导致步数上升。当前用 8 步/素材的额度兜底，
   若实测超限，优先放宽 `DETAIL_LOADED` 的补查次数，而不是放宽 `BLOCKED` 的保存限制。

## 6. 结论

本轮共提出 18 条意见，采纳 15 条、部分采纳 1 条、不采纳 2 条（理由见第 3 节）。

修正后，两份文档在以下四点达成一致：
**六个验收点各有实现任务与证据文件；一票否决项有结构性防护而非提示词约束；
ReAct 证据来源与 Mock 边界表述诚实；P0 范围与 176 分钟预算匹配。**

未解决的核心矛盾只有一个：**高安全设计与 3 小时预算的冲突**。
本轮的取舍是——把安全机制分成"结构性防护（P0，不可砍）"与"证据性防护（P1，可延后）"，
前者保证不犯否决项，后者只在时间允许时补齐。
